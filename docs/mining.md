# XMRig Mining Workload

Lattice runs XMRig as a constrained workload rather than exposing a remote command primitive.

## Trust boundary

A mining lease is accepted only when all existing signed lease, artifact, and runtime checks pass. The runtime ID must be `xmrig`, the runtime version is immutable, and the cached runtime is hashed again immediately before every process start or restart.

Mining also requires both local and remote policy to allow mining. The effective policy may only reduce the local user's permissions and resource limits.

## Structured parameters

Mining jobs use the signed `JobOffer.parameters` map, but the node parses it into a typed `MiningConfig` and rejects every unknown key.

Required parameters:

- `algorithm`
- `pool`
- `wallet`
- `worker`
- `threads`

Optional parameters:

- `password` defaults to `x`
- `huge_pages` defaults to `true`
- `tls` defaults to `false`
- `keepalive` defaults to `true`
- `donation_level` defaults to `1`
- `restart_limit` defaults to `3` and is capped at `5`

No command, raw argument, executable path, shell fragment, or external config path is accepted from the control plane.

The requested thread count must fit both the node's logical CPU count and the signed job CPU percentage limit.

## Managed XMRig configuration

The node creates an isolated job directory under the node data directory and writes a managed `config.json` there. The generated configuration:

- disables config autosave and watching
- runs in the foreground
- enables only the CPU backend
- configures huge pages from the typed lease parameter
- configures exactly one pool
- binds the XMRig HTTP API to `127.0.0.1` only
- emits periodic hashrate and health reports

The supervisor launches only the verified runtime cache object and supplies only managed arguments generated by Lattice.

## Supervision

Each mining process receives:

- an isolated working directory
- captured `stdout.log`
- captured `stderr.log`
- a sanitized environment
- kill-on-drop containment
- graceful termination followed by a forced-kill timeout
- bounded exponential crash restart

Windows uses a dedicated process group and `CTRL_BREAK_EVENT` for the graceful phase. Unix uses a dedicated process group and `SIGTERM`.

## Lifecycle

The mining executor integrates with the signed job lifecycle:

`Accepted -> Preparing -> Running -> Stopping -> Completed`

Preparation or runtime failures transition to `Failed`. Unexpected process exits may restart up to the signed bounded restart limit before the job is failed.

A node shutdown, lease expiry, or policy revocation stops the miner.

## Telemetry

While XMRig is running, Lattice polls the loopback-only XMRig summary API and exposes:

- current hashrate
- recent average hashrate
- accepted shares
- rejected shares
- XMRig uptime
- algorithm
- pool
- worker
- CPU thread count
- restart count

Wallet and pool password values are not exposed through mining telemetry.

## Runtime packaging

The XMRig runtime registry entry should reference the executable payload itself, not a ZIP archive. Lattice treats that executable as immutable content identified by its signed SHA-256 digest, version, platform, and architecture.
